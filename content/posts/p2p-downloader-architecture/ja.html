01ダウンローダーが本当に解決すべき問題

数百件のダウンロードを一度に追加すると、すぐに始まるものもあれば、ソースが見つからないもの、多数の相手に接続しているのにほとんど進まないものもある。同時ダウンロード数を増やすと改善する場合もあるが、ディスク負荷とメモリ使用量が増えるだけで、正常だったダウンロードまで遅くなる場合もある。

これは、ダウンローダーが異なる種類の問題を同時に扱っているためだ。何を探しているのか、必要な部分を誰が持っているのか、相手は今転送できるのか、ローカル側は受け切れるのか、受け取ったデータは正しいのか。それぞれにかかる時間とコストは異なり、整然とした順番で一斉に完了するわけではない。

本稿では、複数の P2P プロトコルに対応するダウンローダーの設計を例に、全体構成から順に説明する。BitTorrent と eD2k／Kad は実際のプロトコル動作を説明するために用いる。一方、9 つのコンポーネント、2 つのループ、動的ダウンロードプールは、それらの機能を構成するための一つのアーキテクチャ上の選択である。

まず、システム内でのデータの形を区別する

用語 ダウンロード処理での意味
タスク（Task） コンテンツ全体または一部を取得したいというユーザーの意図。選択したファイル、保存先、一時停止状態を含む。一つのタスクが時間の経過とともに多数のソースと接触することもある。
ソース／ピア（Peer） データを提供する可能性がある相手。検索結果の候補、接続済みのソース、実際にデータを送っているソースは、それぞれ異なる段階にある。
メタデータ（Metadata） ファイル構造、サイズ、分割方法、検証情報など、コンテンツを説明するデータ。何を要求するか決めるには、まずコンテンツの構造を理解する必要がある。
ピース／パート（Piece／Part） プロトコルが記述や検証に使うデータ単位。転送時には、さらに小さい block に分けることもある。異なるプロトコルの単位をそのまま混用することはできない。
ファイルデータ（Payload） 実際に保存したい内容。ハンドシェイク、ソース一覧、keepalive などの制御メッセージもネットワークを使うが、ファイルの進捗とは異なる。

BitTorrent では、ピアが保有するピースの情報を交換し、受信側がデータを要求する。受信したピースは、さらにメタデータに基づいて検証する。この仕組みにより複数の相手から同時に取得できるが、「接続がある」「通信量がある」「正しい新規データがある」は別々に観測する必要がある。[01]

このアーキテクチャの中心は、不足データを着実に減らすことにある。

接続数、タスク数、帯域使用率は、判断を助ける指標にすぎない。本当の成果は、必要な内容が少しずつ届き、検証を通過し、中断後も引き続き利用できることである。

02全体構成：9 つのコンポーネントの連携

この構成を理解するには、まず三つの点を見る。制御上の判断はどこへ流れ、ファイルデータはどこへ流れ、状態はどこに保存されるのか。ユーザーが一時停止を押したときは、あるタスクの実行意図を変えればよい。ダウンロード中の数 GB のデータはプロトコルエンジンが継続して処理し、管理画面やデータベースを経由して転送する必要はない。

コンポーネント 扱う問題 他のコンポーネントとの関係
P2P Web View 進捗、ソース、待機理由を表示し、タスクを操作できるようにする。 Manager を通じて意図を伝え、状態を取得する。
P2P Manager 操作を受け付け、タスクを識別し、利用可能な Component を管理する。 意図と状態を調整し、永続化が必要な変更を Store に渡す。
P2P Config 一貫した有効設定とソースカタログを提供する。 各コンポーネントを同じポリシーで動かし、更新の理由を残す。
P2P Search コンテンツ検索、識別情報の解決、継続的なソース探索を行う。 各プロトコルの Search Provider から手掛かりを取得し、スケジューリングに供する。
P2P Scheduler どのタスクを試行・継続転送させ、どれに一時的に資源を譲らせるかを決める。 ソース情報とローカル負荷に応じてタスクの資源枠を割り当てる。
P2P Component 実際のプロトコルとダウンロードエンジンを接続する。 共通の管理意図をエンジンが実行できる操作に変換し、ネイティブ状態を報告する。
P2P Store タスク、コンテンツ識別、ソース概要、ポリシー、復旧記録を保存する。 復元可能な事実を SQLite に保存する。ファイル内容はエンジンが管理する。
P2P Metrics 速度、遅延、キュー、資源圧力の時間変化を保存する。 処理の分析を助ける。リアルタイム制御には別の直接報告経路がある。
P2P Connection Manager 各接続の役割、サービス状況、異常の証拠を把握する。 範囲を明示した接続制限を提案し、Component 内のエージェントが実行する。

論理的な役割分担とプロセス配置は別々に決められる

9 つの名前は 9 種類の責務を表すのであって、最初から 9 つのサービスに分ける必要はない。一つの Rust 常駐プロセスに Manager、Search、Scheduler、Connection Manager、Store の調整ロジックを置ける。各ネイティブエンジンは、組み込み能力、言語、障害分離の要件に応じて、同一プロセスまたは独立した Component host に配置する。

同一プロセス内の呼び出しとデータ交換は直接的で、配備も単純になる。独立プロセスなら、エンジンのクラッシュ、ネイティブライブラリ、資源制限を分離できるが、通信、再起動、状態同期は複雑になる。プロセスを分けるかどうかは、構成図の箱の数ではなく、こうしたコストで判断すべきである。

一つのダウンロードタスクに一つのエンジンプロセスを対応させる必要もない。複数のタスクは通常、エンジンの実行環境、接続管理、ソース探索設備を共有できる。タスク数の増加で主に増えるのは状態と実際に必要な資源であり、システム全体を何倍にも複製することではない。

03Component が異なるプロトコルをつなぐ仕組み

多プロトコルのダウンローダーで陥りやすいのは、すべてのプロトコルを同じ「開始・一時停止・進捗率」に置き換えることだ。操作は統一されたように見えるが、BitTorrent の choke、eD2k のリモートキュー、ソースへの到達性、エンジンが本当に一つの接続だけを閉じられるか、といった重要な情報を失ってしまう。

Component はこれらの違いを残しながら、上位層が共通の問いで管理できるようにする。今取得できるデータは何か、転送にどれだけ資源が必要か、止めると何を失うか、観測中の待機はリモート制限かローカル要因か、という問いである。

プロトコルの機能を適切な場所に置く

内部の役割 責務
Search Provider そのプロトコルの検索・ソース探索方式を取り込み、出所、観測時刻、ネイティブ項目を保持する。
Downloader 「このタスクを試行する」「資源を減らす」「保存して一時停止する」をエンジン操作へ変換し、実際に反映されたか追跡する。
Engine ネットワークプロトコル、メッセージ解析、ピース要求、再試行、検証、ネイティブ再開機能、ファイル I/O を扱う。
Connection Agent エンジンが観測できる接続状態を上位へ報告し、実際に対応している切断や制限を実行する。
資源と観測の報告 タスク、接続、ローカル負荷を整理する。即時概要は制御コンポーネントへ、履歴サンプルは Metrics へ送る。

三つの判断層が、それぞれ一つの問いに答える

Scheduler は「どのタスクにどれだけ資源を渡すか」、Connection Manager は「今どのソースや接続を使うのが適切か」、Engine は「今どの相手にどのピースを要求するか」を決める。この分担なら、外側はホスト全体の負荷を管理し、エンジンはプロトコルの即時状態に応じて個々の要求を処理できる。

例えば Scheduler がタスク A の継続を許可しながら、Connection Manager がタイムアウトを繰り返すソースの一つを一時的に避けることができる。Engine は他のソースからピースを要求し続けられる。一方、ユーザーがタスク A を一時停止したなら、どの層も「速いソースが見つかった」という理由で転送を再開してはならない。

情報が見えることと、同じ細かさで操作できることは別

外部エンジンの管理 API は torrent 全体の概要しか提供しなくても、下位ライブラリにはピア単位のピースや要求情報がある場合がある。この二つの能力を混同してはならない。同様に、IP の遮断と現在の接続だけを閉じる操作では影響範囲が違うため、アダプター層はその差を残す必要がある。

具体例が qBittorrent である。本稿が参照する固定ソース版では、banPeersAction() はエンドポイントを解析した後に banIP() を呼び出す。そのため、この操作を一つの接続だけに作用するボタンとして包み込むことはできない。ここでは当該版の動作を、アダプターの能力差を示す例として引用している。[18]

情報が不足していても、上位層は粗い粒度のタスク割り当てを行える。ただし、観測していない詳細まで推定してはいけない。架空のゼロ通信量や精密な操作を表示するより、「エンジンから提供されていない」と示す方が役に立つ。

04コンテンツを見つけることと、転送できる相手を見つけること

ソース探索の前に、同じコンテンツを指しているか確認する必要がある。ファイル名は表示情報にすぎず、同名でも内容が違うことや、異なる名前が同じデータを指すことがある。多プロトコル環境では、hash のアルゴリズムや分割方法が違うだけでなく、そもそも別の種類の対象をハッシュ化している可能性もある。

infohash は torrent のコンテンツ記述を識別する

BitTorrent v1 の infohash は、info dictionary の元の bencoding に対して SHA-1 を計算した値である。この dictionary は内容構造とピース検証情報を記録する。infohash はその要約であり、ダウンロードするファイル全体を直接 SHA-1 にかけたものではない。v2 では infohash に SHA-256 を用い、ファイルごとの Merkle tree でデータ検証を構成する。[01][03]

したがって、ファイルの bytes が完全に同じでも、torrent の記述が違えば別の torrent になり得る。複数ファイルの torrent で「二つのファイルだけを選ぶ」のは別の層の話であり、torrent の識別は変わらないが、そのタスクで不足する範囲が変わる。

システムでは、コンテンツの識別、選択範囲、所属するネットワーク範囲を別々に保存する価値がある。BitTorrent、eD2k などの識別子を、文字列が似ているだけで統合してはならない。プロトコルをまたいでデータを再利用するには、内容の対応、分割位置、検証方法も確認する必要がある。

magnet が「メタデータ取得中」で止まりやすい理由

magnet にはコンテンツ識別と少数の探索手掛かりだけが含まれ、完全なファイル構造はない場合がある。クライアントはまずピアを見つけ、metadata exchange で info dictionary を取得し、既知の infohash と一致するか検証する。BEP 9 が転送するのはこの部分であり、.torrent 全体の最上位項目すべてではない。v2 の検証では、対応するハッシュ情報も扱う必要がある。[02][03]

この時点でファイル進捗が表示されないのは自然なことだ。システムは後続の要求に必要な情報を構築している。利用可能なピアが一つもなければ、転送予算を増やしてもメタデータは手に入らない。

ソース探索方式ごとに、扱う索引が異なる

方式 ソースの見つけ方 混同しやすい点
BitTorrent Tracker クライアントが tracker に swarm への参加を通知し、ピアの連絡先を取得する。 Tracker の応答はソース情報であり、通常、ファイルデータはピアが転送する。[01][08]
BitTorrent DHT 既知のノードを起点に、infohash に対応するピア情報を検索する。 Mainline DHT は汎用のキーワード検索エンジンではなく、ダウンロード対象ファイルを直接保存するものでもない。[04]
PEX 接続済みのピア同士が、他のピアの連絡先を交換する。 最初の接点が必要であり、初めてピアを見つける問題を単独では解決できない。[05]
eD2k Server ファイル検索とソース索引を提供し、一部の接続確立も支援する。 索引サービスとピア間の実ファイル転送は別の役割である。[19]
Kad 分散索引でファイルとソースを探す。参加時には既知の連絡先ノードが必要になる。 *Mule 系では Kad と eD2k のソース探索は異なるが、ファイル転送の仕組みは共有できる。[11]

したがって上位の Search は、「キーワードでコンテンツを探す」と「識別子を基に利用可能なソースを探す」の両方を扱える。ただし、すべてのプロトコルが同じ検索能力を持つと仮定してはならない。他のネットワークへ拡張するときも、それぞれの索引、待ち行列、識別モデルを保持する必要がある。

プライベート torrent には独自のソース境界がある

metainfo に private=1 が明示されている場合、BEP 27 はプライベート tracker のソース範囲内での動作を要求する。一般の公開 torrent と同じように DHT や PEX などでソースを拡散してはならない。[06]

メタデータ取得前の「プライベートか未確定」という状態も、公開 tracker を自由に追加してよいことを意味しない。この構成では元のソースと探索ポリシーを一緒に保持し、全体的な「ソースを増やしたい」という意図が個々のタスクのプライバシー範囲を越えないようにする。

05大量ダウンロードに二つのループが必要な理由

一度に 1,000 件の対象を追加するとする。ダウンロード枠に入ったタスクだけがソースを探せるなら、先頭の数件が長時間応答を得られないだけで後続も停滞する。反対に、1,000 件すべてに直ちに大量の接続を作れば、今度はローカル資源が先に尽きてしまう。

二つのループは、この二種類の処理を分離する。探索ループはソース情報を維持し、転送ループは現在の証拠と資源に応じて実際のデータを取得する。受理した対象はすべて探索スケジュールに参加できるが、実際に同時発行する照会と接続は資源制御を受ける。

900 番目が先に結果を得たら、900 番目から処理する

探索はバッチ全体の完了を待つ必要がない。1 番目の tracker がまだ応答していなくても、900 番目が不足ピースを持つピアを見つけたなら、先に試行へ進める。各結果を独立して更新し、「全員の応答後に続行する」という条件は設けない。

これはすべてのソースを繰り返し照会するという意味ではない。同じ内容でネットワーク範囲とポリシーが互換なら、重複するソース照会を統合し、異なる選択範囲で結果を共有できる。Tracker transport、DHT ルーティングテーブル、eD2k server session にも共有できる部分がある。取得中の metadata に対して、同じ処理をもう一つ作る必要は通常ない。

手掛かりを保存し、適切な時点で接続を解放する

一回の探索で、ソースアドレス、保有を申告した範囲、現在のサービス状態、観測時刻を残せる。短い接続が終了しても手掛かりは残り、次に必要なときの再試行先を絞れる。

ただしソース情報には鮮度がある。5 分前に接続できたピアが今はオフラインかもしれず、その時不足していたピースも別の相手から取得済みかもしれない。古い情報は「誰から照会するか」の判断には使えるが、「今必ずダウンロードできる」証拠には向かない。スナップショットの期限切れはソース判断にだけ影響し、ローカルの検証済みデータを無効にはしない。

探索には独自の周期がある

再照会の頻度はプロトコル自体によって制限される。Tracker 応答の interval、PEX の更新周期、eD2k の再問い合わせ機構は、次の適切な照会時刻に影響する。全体スケジュールで順序を決めたり重複処理を統合したりはできるが、密な再試行で相手の待機ポリシーを消すことはできない。[01][05][12]

探索と転送を分けると、処理中のシステムでも新しい機会を発見でき、ソースが一時的に少ないタスクが完全な転送資源を長期間占有せずに済む。

06短いプローブと、実際の接続コスト

本格的な転送前に短いプローブを行うと、相手への到達性、対象内容への正しい応答、保有ピースの申告、現在のキュー待ちなどを確認できる。次に試す価値のあるソースを選ぶ手掛かりになる。

ただし、プローブが答えられる問いには限りがある。TCP 接続が速く確立しても、分かるのは今回の接続確立が速かったことだけである。相手のアップロード帯域、サービスの安定性、データ完全性は証明できず、有用なデータを実際に要求する必要がある。

「プローブ」と half-open は異なる概念

libtorrent の connecting は接続確立中の half-open 状態を指し、handshake は接続が開き、プロトコルのハンドシェイクを待っている状態を表す。bitfield などを得る段階では、通常、単なる接続確立はすでに終わっている。[09]

そのため本稿では、この処理を「短いプローブ session」と呼ぶ。意図的に TCP を未完了状態で止めても、必要なプロトコル情報は得られず、資源消費もなくならない。UDP tracker、DHT、transport を共有する仕組みでは、一回の論理プローブを独立した TCP socket 一つと直接数えることもできない。

同時に維持する数と、毎秒の追加数を別々に制御する

一方の制限は同時保有量を管理する。現在維持しているプローブが使うファイル記述子、メモリ、エンジン状態の量である。もう一方は追加レートを管理する。古いプローブがすぐ終わっても、同じサービスへ一秒間に大量の新規接続を作ってよいわけではない。

ファイル記述子（FD）は、OS が開いたファイルや socket などの資源を追跡するための番号であり、その余裕は制限の一つにすぎない。Token bucket は毎秒許可する追加回数を消費可能なトークンに変え、瞬間的なバーストも制限できる。両者を組み合わせて初めて、常駐コストと短時間の負荷を同時に抑えられる。

単純化した資源見積もり

この種のプローブが各自独立した socket を一つ使うとする。残りの FD は 300 件分、専用メモリの余裕は 24 MiB、1 件当たりの推定コストは 64 KiB なら、メモリは約 384 件を支えられる。同時に存在できる数は、まず FD の 300 件という制約を受ける。

新規プローブ数 ≤ min（残りの並行枠、全体の利用可能トークン、そのソースの利用可能トークン）

今回のトークンが 16 個なら、並行枠が 150 件空いていても追加できるのは最大 16 件である。これは二種類の制限を説明する算例で、推奨設定ではない。socket を共有するプローブでは、実際の資源に合わせて計算し直す必要がある。

実コストはプロトコルや応答サイズで変わるため、見積もりに加えて、接続タイムアウト、メモリ増加、イベント処理遅延、資源割り当て失敗も観測する。NAT 追跡表や一時ポートの容量は直接見えないこともある。失敗率が上がったら、無制限と仮定するより、追加数を保守的に減らす方が確実である。

プローブ終了時に解放するのは、解放可能な資源だけ

ソース情報を取得し、維持すべきネイティブ状態がなければ、一時接続は閉じられる。しかし共有 server session、DHT の経路状態、価値のある待機資格はプロトコルに従って扱い、プローブのたびにすべて破棄してはならない。

特に eD2k では、キュー状態と持続的な TCP 接続は一対一ではない。再問い合わせや queue rating などは UDP を使う場合もある。接続維持の要否や再問い合わせ時刻はネイティブエンジンの仕組みに従うべきで、「切断すると必ず列から外れる」「切断には一切コストがない」と一般化してはいけない。[12]

07ソースが多いのにダウンロードが完了しない理由

ソース数から分かるのは候補数だけで、全内容を取得できるかは直接分からない。本当に有用な問いは、ローカルで不足しているピースは何か、現在のソースを合わせればそれらを提供できるか、である。

完全な seed は全ピースを持つため、通常は分かりやすい好材料となる。しかし単独の完全なソースがなくても、相補的な部分を持つ複数のピアで完成できる場合がある。逆に、数百のソースが同じ末尾ピースを欠いていれば、進捗は止まったままである。[12]

二つの比率で「すでにある」と「まだ取得できる」を区別する

ここでは S をタスクに必要なデータ範囲、V をローカルで検証済みの範囲、Aⱼ を j 番目のソースが最近提供可能と申告した範囲とする。これらの集合は互換性のあるネイティブ検証範囲で表す。複数ファイルの内容では、ピース境界も考慮する必要がある。

不足範囲 M = S − V
観測被覆率 = bytes［(V ∪ ⋃Aⱼ) ∩ S］／bytes(S)
不足部分の供給率 = bytes［(⋃Aⱼ) ∩ M］／bytes(M)

ここで bytes() は範囲のバイト数を数える。例では各ピースが等しい大きさなのでセル数で計算できるが、実ファイルの末尾は短い場合があり、単純なピース数では誤差が生じる。M が空なら必要なデータは検証済みであり、保存と完成ファイルの確定へ進む。ゼロを分母にする必要はない。

第一の比率は、検証済み部分と現在のソース申告を合わせて必要範囲のどれだけを覆うかを示す。第二の比率は不足分だけを見る。どちらもピアの申告を検証済み進捗に格上げしてはならない。ピース一覧を提供しないプロトコルなら、状態は不明のまま残し、実際の転送で判断材料を補う。

希少ピースは瞬間的な速度より重要な場合がある

例のソース C は遅くても、他のソースにない 10～12 を持っている。MiB/s だけで順位を付け、4～9 しか持たない高速ソースに置き換えると、短期の通信量は増えても、ファイル全体を完成させる可能性は下がることがある。

全体スケジュールが希少データを得る機会を残すべき理由はここにある。Engine は一つのダウンロード内でのピース選択を担い、Scheduler はタスク間の資源を調整して、希少ソースを含むタスクが高スループットのタスクに完全に押し出されるのを防ぐ。libtorrent の piece picker は希少度や優先度を考慮するが、全体の公平性は別の層の問題である。[10]

08ピアのデータが利用可能なファイルになるまで

ソースが見つかってから、実際のデータ経路が動き始める。Engine は既知のピース、未完了要求、ネイティブなサービス状態に応じて、次に誰から何を取得するかを決める。外側のダウンロードプールが資源範囲を与え、細かな選択はエンジン内に残す。

Piece は検証単位、block は要求単位

BitTorrent v1 では metadata に各 piece のハッシュがある。転送時は、一つの piece を複数の小さな block 要求に分割できる。block が届いた段階では、その受信範囲を記録できるだけで、通常は piece 全体をそろえてからハッシュと照合する。[01]

これは piece 全体を常にメモリに保持するという意味ではない。エンジンは先に partial ファイルへ書き、後から読み出すか、利用できるデータを再利用して検証できる。受信・書き込み・検証は交錯して進むため、「受信済み」だけでは安心して再利用できるとは限らない。

状態 分かっていること まだ仮定できないこと
受信済み あるデータ範囲がローカルに届き、明白なメッセージや範囲の誤りは除かれている。 内容ハッシュの検証を通過したとは限らず、バッファ内だけに存在する可能性もある。
検証済み プロトコル上で十分な情報が得られ、内容が期待する検証値と一致している。 データと再開記録の両方が耐久的に保存されたとは限らない。
復元可能な保存済み状態 データと対応する状態が保存手順に従って同期され、再起動後に照合・再利用できる。 これだけで全ファイルの完成や、内容を安全に実行できることまでは推論できない。

未完了要求を複数同時に保持する理由

要求を一つ送り、受信してから次を送る方式では、ネットワーク往復の待ち時間に空白ができる。Pipelining は複数の要求を飛行中に保ち、前のデータが戻る間に後続を処理させる。BitTorrent の仕様にも、この方法が明記されている。[01]

要求ウィンドウと RTT の関係

理想化した見積もりでは、10 MiB/s を維持し、要求の往復遅延が約 100 ms なら、応答待ちだけで停止しないためには、約 1 MiB の飛行中データを収容する必要がある。

飛行中データ量 ≈ 目標レート × 往復時間
10 MiB/s × 0.1 s = 1 MiB
1 要求が 16 KiB なら、約 64 件の飛行中要求が必要

これは規模感を示す計算にすぎない。リモートキュー、輻輳制御、ネイティブな要求上限、パケット損失、ローカル buffer が実際の結果に影響するため、64 を普遍的な最適値と考えてはならない。KiB と MiB は、それぞれ 2¹⁰、2²⁰ bytes を表す。

要求ウィンドウが小さすぎると待機によって帯域が遊び、大きすぎると buffer が増えてキャンセルや再配分の反応が遅くなる。「ネットワークを使い切れていない」ときは、他のタスクを増やす前に、既存ソースの要求パイプラインを確認できる。

プロトコルごとの検証粒度は復旧コストにも影響する

BitTorrent v2 はファイルごとのハッシュを SHA-256 Merkle tree で構成し、木の関係を通じてデータを期待する root と対応付ける。*Mule の AICH は、信頼できる root と復旧データが利用可能なとき、破損 part 内の小さなブロックを特定して正しい部分を残し、再取得量を減らす。形式と信頼の根拠は異なるため、同じ交換可能な hash tree として扱ってはならない。[03][13]

ハッシュ一致が示すのは、データが期待する識別と一致することだけである。最初に選んだ内容自体が信頼できなければ、正確にダウンロードしても自動的に安全なプログラムやファイルにはならない。

重複データが完了を早めることもある

ダウンロード終盤で残り block が少なくなると、一つの遅いソースが完了を遅らせ得る。BitTorrent の endgame では、残りデータを複数のソースへ要求し、一つ受信した後で他の要求を取り消せる。取消メッセージと応答が行き違い、遅れて重複 block が届くこともある。[01][07]

そのため、計測では「ネットワークで受信した bytes」「重複していない必要データ」「検証済み進捗」を分けられる。重複にはコストがあるが、終盤の待機短縮につながる場合もある。重複率だけを見て、ソースが意図的に帯域を浪費していると判断してはならない。

09試行：本当に必要なデータで判断材料を得る

ソース探索で得られるのは手掛かりであり、試行では実際のサービス状況が見える。タスクで本当に不足する範囲を取得するため、内容が正しければ後続のダウンロードでも使える。無関係なデータを別途ダウンロードして速度を測る必要はない。

試行の目的は、永久に固定された速度順位を作ることではない。現在のネットワーク、ローカル負荷、プロトコル状態の下で、そのソースの組み合わせが投入に見合う新規データを継続的にもたらすかを判断することにある。

接続成功・サービス開始・データ受信は別の観測点

ハンドシェイクが速くてもキュー待ちのソースや、開始は遅くても始まれば安定するソースがある。接続確立時から一律に「データを送らない時間」を数えると、ネイティブな待機と実際の要求タイムアウトが混ざってしまう。

「サービス可能」は相手による帯域保証ではなく、その要求を出せる条件がそろっているという意味にすぎない。BitTorrent の通常の choke は転送を制限するが、Fast Extension の交渉後は allowed-fast により choked 状態でも特定ピースを要求できる場合があり、明示的に拒否される可能性も残る。したがって資格は、具体的な要求と交渉済みの仕組みに基づいて判断する。[07]

サンプルが足りないときは不確実性を残す

試行の資源ウィンドウ内で完全な検証単位を取得できなければ、結果は「検証待ち」であってデータ誤りとは限らない。サービスを始めたばかりの長 RTT ソースも、一度の短い観測だけで結論を出すべきではない。新規データ、検証の進展、遅延、重複量、ローカル干渉を一緒に見て、コストに応じて観測を延長するか判断する方が合理的である。

小さなファイルが試行中に完成したら、そのまま検証と保存へ進めばよい。低速でも希少ピースを持つソースは、サービス継続に価値がある場合がある。その価値を一定の MiB/s 閾値だけで表すことはできない。

タスク状態は、何を待っているか説明するためにある

段階 実際の意味 次の機会
ソース収集 metadata または新たなソースの証拠を取得中。 利用可能な結果が一つ戻れば、独立して次へ進める。
準備／試行 試す価値のあるソースがあり、有限の資源枠を待つか使用している。 実際の進捗とコストから、継続・延長・譲渡を決める。
継続転送 有用なデータを取得中で、資源にも余裕がある。 欠落ピース、ソース、ローカル負荷の変化に応じて調整する。
観測待機 ソース不在、重要ピースの欠落、リモートキュー、または一時的な低効率。 新ソース、待機期限、または公平な交代で再試行の機会を得る。
一時停止／ローカル保留 ユーザーの一時停止、ローカルエラー、または実行結果が未確認。 原因解消後に再開する。ソースのサービス評価は下げない。
転送完了 要求したデータのネイティブ検証が完了している。 保存と完成先を確認し、意図に従って共有を続けるか停止する。

これらの段階とソース品質は二つの異なる軸である。「不完全なソースだが希少ピースを取得中」も「一時停止中だがローカルの完成ピースは有効」も自然な状態だ。一つの良否スコアに押し込むと、説明力が失われる。

10ダウンロードプールの拡大・縮小と公平な交代

動的ダウンロードプールは、観測を続けるフィードバック制御器と考えられる。まず一部のタスクに資源を与え、進捗と圧力を見て、次の動作を決める。転送中のタスク数は、この過程の結果である。

Scheduler 内部の処理は三つに分けられる。PoolSupervisor が現状を集約し、容量制御器が全体の投入量をどれだけ増減するか決め、交代機構が候補と資源を譲るタスクを選ぶ。これらは内部責務の名前であり、同じ全体スケジューリング層に属する。

資源は複数の制約であり、「あと何件ダウンロードできるか」だけでは表せない

5 件のタスクがすべてリモート制限を受け、ネットワークをほとんど使わないこともあれば、別の 1 件だけでディスク一台のランダム書き込み能力を使い切ることもある。そのため、送受信量、書き込み待ち、メモリ、検証処理、CPU、FD を同時に見て、制御操作用の余裕も残す必要がある。

各資源 r について：
投入済み使用量(r) ＋ 新規タスクの推定コスト(r) ≤ 利用可能容量(r) − 予約余裕(r)

これは資源配分の考え方であり、すべてのコストを事前に正確に計算できるという意味ではない。直接制限できる資源もあれば、即時の圧力から調整するしかないものもある。すでに送出し、縮小の反映を確認していない処理は転送を続けている可能性があり、資源が完全に空いたと先取りしてはならない。

ディスクからネットワークへ背圧が伝わる仕組み

到着速度がディスクへの書き込み速度を上回ると、書き込み待ち buffer が増える。増加が続けばメモリを消費し、検証やイベント処理も遅れる可能性がある。そこでピアを増やすと、下流に未処理データをさらに押し付けることになる。

背圧は、下流が追い付かないことを上流へ伝える。まず新規データ要求や転送枠を減らし、飛行中データと書き込みキューを徐々に処理させる。有用な接続はコストに応じて保持でき、プール全体を切断してやり直す必要はない。

圧力にも範囲がある。遅い HDD へ書くタスクは減速が必要でも、別の空いている SSD へ書くタスクは影響を受けないことがある。Linux PSI は CPU、メモリ、I/O 待ちの圧力信号を提供するが、ディスク別スループットの計器でも、利用可能な Internet 帯域の測定器でもない。[16]

観測した状況 合理的な次の一手
ネットワークに余裕があり、ローカルも健全 既存ソースと要求ウィンドウを先に確認し、ソース制約なら見込みのある試行を増やす。
帯域を使い切っていないが、書き込み待ちが増え続ける 対象ディスクへの新規要求を減らし、検証と書き込みを追い付かせる。
タスク追加後も全体の進捗がほぼ変わらない 追加コストと既存タスクへの圧迫を調べ、成果不足なら直近の拡大を戻す。
スループットが安定し、継続的な滞留がない 有効なサービスを維持しつつ、少量の探索と公平な交代の機会を残す。
資源報告が古い、または途絶えた まず観測を回復する。不明を空きと見なさず、エンジン自身の資源制限を維持する。
これ以上利用可能なソースがない 適切な探索周期を維持する。ローカル資源の追加で存在しない供給は作れない。

有効スループットは同じデータ層で比較する

ネットワークインターフェースの通信量には、プロトコルのオーバーヘッド、再送、他プログラムの通信も含まれる。ダウンローダーが受信した payload にも、重複や最終的に検証失敗するデータがあり得る。長期的な成果は「新たに検証完了した必要 bytes／観測時間」で見て、短期的には重複除去後の受信進捗を補助に使える。

両者にはそれぞれ用途がある。検証完了量は確実な成果に近いが、検証単位やスケジュールによって階段状に増える。重複除去後の受信量は反応が速い一方、未検証のリスクが残る。近い負荷の複数ウィンドウで傾向を見る方が、一秒のピーク値で増減を決めるより安定する。

制御器自身が振動を生まないようにする

新しいタスクには接続、キュー待ち、要求パイプラインの立ち上げ時間が必要である。追加直後に成果がないと止め、次の瞬間に空きを見て再開すると、システムは起動コストを払い続ける。

観測の平滑化、拡大後の観測時間、拡大と縮小で異なる閾値を使うことで振動を減らせる。この異なる閾値をヒステリシスと呼ぶ。境界付近の小さな変動で毎回逆向きの操作が起きなくなる。通常の調整は傾向が明確になるまで待てるが、ディスク満杯やエンジンエラーなどの保護イベントは直ちに扱う。

公平性のためには、機会を明示的に残す必要がある

現在最速のタスクだけを残すと、未試行タスクは自分の価値を示せず、希少コンテンツが人気コンテンツの後ろに永久に置かれることもある。プールは少量の資源を予約し、未知のソース、長時間待つタスク、希少ピースに機会を与えられる。

交代の代価も考える必要がある。既存ソースには安定したパイプラインがあり、新ソースはキューに並び直すかもしれない。まず限定的な試行で候補を比較し、成果が低く資源を譲りやすいタスクと交代するのが合理的である。公平性を実現するために、定期的に全ダウンロードを再起動する必要はない。

11Connection Manager が各接続を理解する方法

ダウンロードプールが見るのは全体資源とタスクの成果であり、Connection Manager は個々の接続に焦点を絞る。両者は情報を交換する。全体スケジュールには価値のある資源の情報が必要で、接続分析にはローカルの速度制限、ディスク、他タスクの影響を受けているかという情報が必要である。

このコンポーネントの主な仕事は、断片的な観測を文脈へ戻すことである。通信量ゼロの接続を見るときは、少なくともその役割、要求状態、相手の保有申告、ローカル側の健全性を先に把握する。

ファイル通信量の前に役割を見る

Tracker、DHT ノード、eD2k server、payload peer はそれぞれ異なる仕事を担う。索引サービスで長時間ファイル payload がないのは正常かもしれず、アップロード専用の接続にも受信データの基準は適用できない。探索と転送が共存する場合、役割の分類は特に重要になる。[04][08][19]

観測の観点 先に問うべきこと 判断への影響
役割と関連 索引、metadata、ファイル受信、アップロードのどの接続か。どのタスクに関係するか。 何をすれば役割を果たしたことになるかを決める。
サービス条件 必要な範囲があるか。プロトコル上要求できるか。実際に未完了要求があるか。 今回のデータ応答を期待する根拠があるかを決める。
データと進捗 新規データはどれだけ届いたか。重複量はどれだけか。検証は未完了か失敗済みか。 通信量、成果、完全性の問題を分ける。
ローカルと共通の干渉 速度制限、書き込み詰まり、古い報告、またはネットワーク全体の障害があるか。 システム自身の問題を各ソースの責任にしない。

同じ IP でも、同じ接続や同じ人物とは限らない

接続は再作成され、エンジンは再起動し、一つのエンドポイントが複数のタスクを提供する場合もある。観測がどの実行世代の、どの実接続に属するか追跡する必要がある。そうしないと、遅れて届いた「古い接続を閉じる」操作が、後からできた新しい接続を傷つけかねない。

peer ID、eD2k user hash、エンドポイントアドレス、ローカル connection ID は用途が異なる。プロトコル上のやり取りを関連付けられるが、認証された実在人物の身元とは見なせない。共有 NAT、動的アドレス、再接続により、一つの IP に対する長期評価も粗くなる。

eD2k の High ID／Low ID はさらに別の話で、主に入着接続の到達性と callback 支援の必要性を表す。数値が大きいほど信用が高い、または必ず速いわけではなく、Low ID だから全ファイルデータを server が中継するわけでもない。到達性はソースを得る機会に影響するが、実際にサービスできるかを確認する必要は残る。[14]

分からない項目は「不明」として残す

エンジンによっては、ピア別ピース一覧、書き込み待ち bytes、要求タイムアウト、choke 状態を提供する一方、管理 API では総速度しか見えない場合もある。libtorrent のネイティブな peer_info にはこの種の観測が複数あるが、アダプター API が公開するかは実際のインターフェースによる。[09]

データの欠如は、未観測、API 非対応、報告の期限切れ、検証待ちなどを意味し得る。それぞれの理由を残す必要がある。すべてを 0 と表示すると、「サービス時間を測れていない」が「サービス時間はゼロ」と誤読され、誤ったスケジューリングや遮断につながりやすい。

12通信量ゼロ・不正データ・遮断がそれぞれ意味すること

接続管理では無駄なコストを減らすと同時に、誤った処罰も避けなければならない。一時的に不要な接続を閉じるのは単なる資源解放かもしれないが、ソースが不正データを送ったと判断するには具体的な証拠が必要である。両者は別の処置にできる。

同じ 0 B/s でも原因はまったく異なる

見えている状況 より合理的な解釈 対応の方向
Tracker に payload がない 索引情報を提供する役割であり、ファイル bytes で成果を測るものではない。 照会結果とソースの増分を見る。
リモート側でまだキュー待ち ネイティブなサービス順がまだ来ていない。 プロトコルに従って待機・再問い合わせし、保持コストを測る。
相手はデータを持つが、すべて取得済み 今は必要な新規データをその相手から得られない。 アップロードとソース交換の価値も見て、用途がなければ接続を解放する。
ローカルの速度制限やディスク滞留 受信側がデータを継続して処理できない。 ローカル負荷を修正し、相手のサービス評価を一時停止する。
有効な要求が繰り返しタイムアウト 現在、そのソースまたは経路が信頼できるサービスを提供できていない。 ネイティブ期限に従って取消・再試行し、必要なら一時的に避ける。
多数の接続が同時に停止 共通のネットワーク、エンジン、報告経路の障害かもしれない。 まず共通原因を探し、ソースを一つずつ処罰しない。

ある無応答を評価するには、具体的な未完了要求、プロトコルに沿ったサービス条件、正常なローカル受信環境が最低限必要である。報告が途絶えて観測できなかった時間を、黙ってゼロ速度で埋めてはならない。

ローカル干渉を除外しても、要求タイムアウトが主に示すのは「今回のサービスが達成されなかった」ことである。相手の負荷、経路、プロトコルのスケジュールも結果に影響する。ソース変更や一時回避の根拠にはなるが、それだけで悪意を意味するわけではない。

Keepalive と遅れて届くデータは意味が異なる

Keepalive は接続上の活動を示せてもファイル進捗を増やさず、データ要求への期待を無期限にリセットする理由にはならない。一方、取消済みの要求にも遅れてデータが届くことがある。特に Fast Extension は、取消と応答が行き違う状況を明示的に扱う。[01][07]

したがってエンジンは要求の文脈を保持する必要がある。要求したことがある、取消済み、応答中、一度も要求していない、は同じではない。接続分析はこのネイティブ情報を使い、「現在 outstanding request がない」だけで遅着データを一律に誤判定しないようにする。

Hash failure はまず不一致を示し、その後で責任を絞る

一つの piece の 4 block を A・B・C・D から受け取り、最後の piece hash が一致しなかったとする。結合したデータに問題があることは分かるが、四つのソースが全員故意に誤データを送ったとは証明できない。ローカル書き込み、メモリ、状態対応の誤りも考慮する必要がある。

方法の一つは、疑わしいデータを隔離し、原因を帰属しやすいサンプルを取り直すことである。libtorrent の parole 機構は、失敗した piece に関与したピアへ piece 全体を要求し、判断の根拠を増やす。「再検証して責任範囲を狭める」ことに実用的な価値がある理由である。[09]

証拠に応じて処置の範囲を決める

処置 目的 注意すべき範囲
接続を切断 今回の無用または失敗したやり取りを終える。 現在の接続だけに作用させ、長期的な悪評を付けなくてもよい。
一時的に回避 失敗を繰り返すソースを休ませ、資源を別の機会へ回す。 内容とソースの組み合わせに限定し、期限後に限定的に再試行できる。
隔離 原因を帰属できる無効データやプロトコル違反を扱い、確認を待つ。 証拠が支える識別・ソース・ネットワークの範囲に限定する。
手動の永続遮断 ユーザーの明示的な長期判断を実行する。 影響対象を示す。IP 遮断は同じアドレスを共有する別タスクにも影響し得る。

同じエラー報告の再送を、新しい違反回数として数えてはならない。同じソースが一つの内容で失敗しただけで、分析せずにネットワーク範囲全体の遮断へ広げるべきでもない。解除時は画面のラベルを消すだけでなく、エンジン内の制限が実際に取り消されたか確認する必要がある。

13ソース一覧をどう更新し、どこまで信頼できるか

Tracker や eD2k server の一覧は起動時の候補入口を提供し、ダウンローダーが完全なゼロから始めずに済むようにする。ただし一覧が長いほど独立ソースが多い、実際の取得能力が高いとは限らない。複数の一覧に同じエンドポイントが載り、ドメイン別名や共有基盤で数が水増しされる場合もある。

ソースカタログは、継続的に修正する手掛かりの集合に近い。出所、取得時刻、どの照会が新ソースをもたらしたか、その後サービスできたかを記録する必要がある。候補、到達実績、有効ソースの提供実績、正しいデータの転送実績は、段階的に蓄積される異なる証拠である。

一覧のダウンロードは候補データの取得にすぎない

外部 feed の更新後は、候補を解析して形式と変更点を確認し、段階的に探索へ取り込める。有用な旧版カタログは保持でき、更新失敗で全ソース集合を空にする必要はない。ユーザーが指定した保持・回避ソースには、feed とは独立した理由もある。

ここで Config は一貫した有効ビューを提供し、Component ごとに異なる版の一覧で判断しないようにする。リモート feed はエンドポイントを提供できても、ローカルポリシーの変更権限やコマンド実行能力を得るべきではない。

エンドポイントは接続を引き起こす入力である

ソース情報は最終的に、ダウンローダーからの能動的なネットワーク接続につながり得る。公開ソースがローカル管理画面、内部アドレス、特殊なサービスポートを返すと、クライアントが本来接触すべきでない対象へのアクセスに利用されかねない。これはソース探索における SSRF 型問題に相当する。

公開 Internet ソースでは、アドレス方針が名前解決後の実際の宛先を確認する必要がある。URL の見た目が正常でも、DNS が別のアドレスを返す可能性がある。リダイレクト、再試行、代替の名前解決でも同じ宛先制限を保つ。OWASP も、先に DNS を確認しても、接続時に未確認の名前解決をやり直すと回避の余地が残ると注意している。[17]

もともと LAN 共有を許可するなら、内部ソースは別の明示的な範囲に属し得るのであって、全体ルールで一律に悪意と扱うものではない。公開・プライベート・overlay ネットワークの入口、識別、ソース拡散方式は、それぞれの意味に沿って扱う必要がある。

ソースの価値は新しい機会と実サービスで見る

毎回多数のピアを返す tracker でも、重複や到達不能が大半なら、少数の新ソースを返す tracker より価値が低いかもしれない。適切な頻度の照会一回当たりの独自ソース数、接続可能率、その後必要データを実際に提供したソース数を観測できる。

比率の分母も明確にする必要がある。未照会なら不明であり、ローカルネットワーク全体の停止中の失敗で全ソースを一斉に低評価にすべきではない。UDP tracker の connect 応答だけでは、announce で peers を取得できたとは言えない。両者は別のプロトコル手順である。[08]

正常な転送が証明するのは、現在見えているやり取りだけ

HTTPS は対応する接続の通信とサーバー認証を保護し、内容 hash は期待値との一致を確認できる。しかし、どちらも運営者がやり取りを記録しているかは教えてくれない。BitTorrent の tracker と peer プロトコルには、もともと内容識別と連絡先の交換が含まれる。[01]

したがって、完全にプロトコルに従い正しいデータを送るエンドポイントでも、それだけで監視や記録を否定することはできない。これは可視情報から導かれる限界である。サービス品質、データ完全性、相手の真意は別の問題であり、国、ASN、peer ID、高速転送ではこの判断を代替できない。

クライアントは、不正なメッセージ長、過剰なソース情報の洪水、帰属可能な不正データ、危険な名前やパスなど、見える異常には対処できる。ソース名と metadata も信頼できないテキストとして表示すべきである。見えていない意図については、根拠のない安全確率を示すより、不明と残す方が誠実である。

14一時停止・再起動・命令喪失から一貫した状態へ戻す

長時間動くダウンローダーでは、管理プロセス、エンジン、データベース、ディスクが常に同時に成功するとは仮定できない。一時停止の意図を管理側が記録しても、エンジンは未受信かもしれない。逆にエンジンは止まったのに、応答だけが失われることもある。

そのためシステムは、何をしてほしいかと何をしたと確認できているかを区別する必要がある。この区別により、一時停止中のタスク、終了中の接続、再起動後の状態にも合理的な復旧経路を用意できる。

先に意図を保存し、実際の反映を追跡する

管理側は操作意図と送出待ち処理をまとめて保存してから、エンジンへ渡せる。応答後に実結果を更新する。途中で停止しても、再起動後に未確認操作を把握でき、メモリだけを頼りに推測せずに済む。

一時停止を送った直後に管理プロセスがクラッシュした場合

  1. 意図の保存：タスク A を一時停止したいという操作は永続化済み。
  2. エンジンへ送信：エンジンは新規要求を止め、飛行中データと書き込みを排出中かもしれない。
  3. 応答は未確認：管理プロセスの再起動後、停止が成功したか失敗したかは直ちに断定できない。
  4. 再照合：同じエンジン実行世代の実タスク状態を照会し、結果を更新するか未完了操作を補う。

解放を確認するまでは、このタスクがネットワーク、メモリ、ディスクを使っている可能性がある。資源台帳から早く削除すると、次のタスクへ実際には空いていない枠を渡してしまう。

再送でも同じ操作だと識別できなければならない。そうでなければ、障害後の再試行がタスクの重複追加、同じ証拠への反復処罰、新接続への古い命令の適用になり得る。操作識別、エンジンの起動世代、目標状態は、これらの違いを見分ける助けになる。

SQLite は復元可能な事実、Metrics は時間変化を保存する

タスク、内容識別、有効ポリシー、判断に影響する証拠、ファイル操作記録は Store に適している。再起動後も成立し続ける必要があるからだ。毎秒のピア速度、遅延分布、負荷曲線は Metrics に属し、詳細の保持期間と集計要件に応じて保存方式を設計できる。

保存先 保存するもの 分離する理由
Store／SQLite タスク意図、内容との関連、最近のソース概要、ポリシー、復旧記録。 重要状態を一貫したトランザクションと追跡可能な変更で扱う。
Metrics 速度、遅延、圧力、キューなどの履歴サンプルと集計。 高頻度観測の保持量を独立して制御し、タスク状態の書き込みを圧迫しない。
Engine の作業ディレクトリ Payload、partial、ネイティブ再開データ、ファイル範囲情報。 実際に I/O を行うエンジンが管理し、二つのコンポーネントが同じデータを同時変更しない。

SQLite の WAL モードでは読み書きを並行できるが、同時に存在できる writer は一つである。長い読み取りは checkpoint の進行も妨げ得る。この構成では重要状態の書き込みを集中調整し、トランザクションを短く保つことを選ぶ。責務は明確になるが、データベース外のファイルやエンジンとの一貫性を自動的に解決するわけではない。[15]

履歴監視の故障で健全な転送まで止める必要はない

Scheduler と Connection Manager が必要とする即時概要は、Component から直接報告できる。Metrics が一時的に履歴保存できなくても、この経路でダウンロードを続けられる。観測サンプルは上限付きバッファと明示的な欠測で扱い、監視故障がメモリを使い尽くさないようにする。

Store が新たな重要状態を保存できない場合は影響が異なる。新規割り当てと永続ポリシー変更が信頼できなくなるため、記録が復旧するまでそれらを抑制すべきである。不正メッセージ、失効接続、ローカル資源に対するエンジン自身の即時保護は、独立して存在する必要がある。

経過時間は時計合わせに影響されない単調時計で測り、再起動をまたいで残す日時は別に記録する。再起動中に観測できなかったサービス時間をソースのタイムアウトで埋めてはならず、古いスナップショットも新しいエンジン状態に照らして再確認する必要がある。

15断片的なピースから、完全で復元可能なファイルへ

タスクがプールへ出入りしても、取得済みデータまで消えるべきではない。観測待機へ移すには通常、実行調整と再開状態の保存だけでよい。ファイルを移動すべきという意味でも、削除してよいという意味でもない。

段階的な割り当てと、ファイルの二種類の大きさ

多数の対象を先に登録し、転送が必要になってからデータ領域を増やすと、最初から全対象の全容量を確保せずに済む。ただし空き容量不足が途中で判明する可能性があり、割り当てと I/O の特性もファイルシステムやエンジンに依存する。

論理サイズと割り当て済み空間を区別する必要がある。スパースファイルは論理長が大きくても、未書き込みの穴に同量の物理ブロックを割り当てているとは限らない。また空き容量では、内容だけでなく、再開データ、データベース、一時ファイル、検証、完成時の移動に必要な追加領域も考慮する。

段階的な書き込みは柔軟で、事前割り当ては容量不足を早めに検出し、一部のファイルシステムで割り当ての断片化を減らせる可能性がある。装置、ファイル規模、利用状況で選べるトレードオフであり、すべてのタスクに同じ方式を強制する必要はない。

ファイル名は表示用、保存上の識別は安定させる

作業ディレクトリを安定した内容識別でバケット分けすれば、一つのディレクトリへの集中と同名ファイルの上書きを防げる。識別子にはプロトコルの意味も必要で、異なる hash 空間の文字列をそのまま同じオブジェクトと扱ってはならない。

magnet は完全な metadata の取得前に、一時的な識別で追跡する場合がある。内容の対応が確定したら、タスクとファイル位置の変更を記録し、再起動後も書き込み済みデータを見つけられるようにする。元のタイトルとパスも安全に処理し、ソースが与える ../ や絶対パスにローカルの書き込み先を決めさせてはならない。BitTorrent v2 の仕様にも、この種のパス処理が明記されている。[03]

転送完了後にも、保存と完成ファイルの確定が必要

必要なデータがすべて検証を通過しても、飛行中の書き込み、ネイティブ再開情報、実際のファイル位置を確認する必要がある。100% と表示するだけでデータと復旧記録が不整合なら、再起動後に広範な再検証が必要になり、利用できるデータすら判断できない可能性がある。

対応する意味を持つローカルファイルシステムでは、同じマウント範囲内の rename によって名前の切り替えを原子的に行える。マウント点をまたぐ移動は同じ rename だけでは完了できず、通常は保存先の一時ファイルへコピーし、確認してから完成状態に切り替える必要がある。[20]

名前の切り替えが原子的でも、電源断後に必ず残るとは限らない。Linux では例えば、fsync() がファイルデータと関連 metadata を同期し、ディレクトリエントリの永続化にはディレクトリの同期も必要な場合がある。そのため完全な移動手順では、内容、位置記録、旧コピーを削除する時点を別々に扱う。[21]

装置間コピーの途中で失敗したら、元ファイルを急いで消すより、旧コピーと未完了記録を保持する方が確実である。共有中のファイルはエンジンとパスを調整する必要もある。使用中ファイルを外部から直接移動すると、その後のアップロードや再開で対応を失う可能性がある。

長期間ソースがない場合に、初めて保持方針を検討する

今日ソースがないタスクでも、明日にはピアがオンラインになるかもしれない。末尾が希少な内容も、再共有で復活する場合がある。部分ファイルを整理するかは、長期観測、ユーザーの保持意図、キュー機会の有無、現在の writer や未確認操作を合わせて判断すべきである。

自動整理が必要なら、まず候補を復元可能な隔離段階へ移し、保持期間に基づいて削除を決めると誤判定の代価を減らせる。低速、tracker の一時停止、一つのソースの回避だけでは、全データが価値を失った証拠にはならない。

16現象から原因をたどる

責務分担の価値は、最終的に問題を説明できるかに表れる。「ダウンロード中」と速度だけでは、停止時に推測するしかない。内容、ソース、要求、検証、ローカル負荷を順に見れば、問題をより小さな範囲へ絞れる。

現象 先に確認する証拠 考えられる説明
接続は多いが速度が出ない 役割、不足ピースとの積集合、queue／choke、未完了要求。 索引サービス、待機中のピア、取得済みピースしかないソースに接続している可能性がある。
99% で停止 最後の不足ピース、ソース申告、実際のサービス可否。 末尾を持つソースが極少数、または全ソースが共通して欠落している。同じソースを増やしても改善しない。
帯域が余っているのに追加しない 書き込み待ち、ディスク遅延、検証キュー、メモリ、報告の鮮度。 下流のボトルネックや観測不足により、一時的に拡大が不適切かもしれない。
タスク追加後に全体が遅くなる 追加前後の有効進捗、I/O 変化、buffer、再試行、接続変化。 共有資源の競合が始まり、追加コストが追加成果を上回っている。
大量の通信に進捗増加が見合わない Payload と制御通信、重複 block、検証待ちと検証失敗。 endgame、誤データの再取得、または受信済みだが未検証の可能性がある。
再起動後に再検証が必要 データ、ネイティブ再開記録、最後に確認した同期状態。 ファイルは残っていても旧進捗を直接信用する根拠が足りず、再検証で利用可能性の証拠を作り直している。
ソースが復旧してもタスクが始まらない ユーザーの一時停止、ローカル保留理由、クールダウン、利用可能枠、新ソースの照合状況。 ソースの存在は条件の一つにすぎず、他の制限が有効な可能性がある。
画面で遮断解除しても接続できない エンジン内ポリシーの取消、ソースへの到達性、ネイティブ再試行間隔。 表示と実行が同期していないか、そもそも失敗理由が遮断だけではなかった。

画面には状態名だけでなく理由を示す

ダウンロード一覧には現在の段階と主な待機理由を表示し、詳細で不足範囲、ソース分布、要求状況、ローカル圧力を補える。接続の詳細には、提供したデータ、観測時刻、制限理由、操作をエンジンが確認したかを残す。

これにより、ソース待ちやリモートキューなのか、HDD の書き込みが追い付かずローカル背圧を受けているのかを区別できる。ソース情報が不明な場合も、未観測なのか、エンジンがそもそも提供しない項目なのかを見分けられる。

一つのダウンロードで全体構成をつなぐ

ユーザーが内容を追加すると、Manager が意図を保存し、Search が対応する Component を通じて metadata とソースを取得する。準備できたタスクは限定試行へ入り、Engine が許可されたソースと資源枠の中でピースを要求する。実進捗とローカル圧力は Scheduler へ、接続のサービス状況は Connection Manager へ戻る。

有用なデータは蓄積し、価値のない投入は徐々に減らす。新ソースの発見機会を維持し、長時間待つタスクや希少ピースを持つタスクにも機会を残す。Store は重要状態を復元可能にし、Metrics は過去の変化を分析可能にする。最後に選択した内容の検証が終わり、データと保存状態が一致したら、完成ファイルを確定して位置を更新する。ダウンロード中に検証したピースも、ネイティブプロトコルとユーザーの意図に従って共有し続けられる。

これらの責務が明確につながることで、ソース変動、ネットワーク待機、ディスクのボトルネック、プロセス中断の中でも、根拠ある判断を続けられる。次に速度が落ちたときも、どの段階で詰まり、何が変われば進むのかをシステムが示せるべきである。
