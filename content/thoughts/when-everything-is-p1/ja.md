まだ AI がなかった時代を振り返る。
プロジェクトを進めるとき、みんな何かと P1 を付けたがるので、Ticket のほとんどが P1 になっていた。
全部が P1 なら、P1 はないのと同じ。

社内システムの改善は、たいてい想像よりも遅い。当時、Ticket の順番を決めても、99％の確率で予定からずれていた。
いろいろな P1 が割り込んできて、もともとの P1 はというと……やっぱり P1 のままなんだよね XD
そのうち、上が今日はこれが重要だからこれを先にやれ、明日はあれが重要だからあれを先にやれと言うようになり、開発がひどく細切れになった。

私もソフトウェアエンジニアを約 5 年やって、シニアエンジニアになった。
幸運だったのは、AI が登場したときには、すでにエンジニアだったこと。
ずっとコードの簡潔さと明瞭さを追求してきて、リファクタリングに多くの時間と労力を費やしてきた。
コードの品質と効率を追求し、拡張しやすく、可用性が高く、疎結合なコードを開発する。
だから AI 以前の時代から、優れたオープンソースのコードをずっと読んでいた。

でも正直、今の AI が書くコードが人間の書くコードより劣っているとは思わない。
むしろ、大半の人のコードの品質は、現時点の Opus 5.5 が書くコードよりひどい。基本的な SOLID や Pattern すらまともに使えていない。
OOP を追求しても抽象化が過剰になり、ML を追求した結果もぐちゃぐちゃになる。

だから、もし「AI が生成した Code は心配じゃないの？」と聞かれたら、
逆に聞きたい。「あなたの同僚が書いた Code なら安心できるの？」と。

問題の本質は同じ。それなら、強力な E2E と AI による検出に頼って、この問題に対処すればいい。

それに、ソフトウェアエンジニアリングにおいて学位はあってもなくてもいいもの（面接では必要だけど）。ソフトウェアエンジニアリングはたいてい経験がものをいう仕事で、何を知っているかより、何に対処できるかのほうが重要。
経験がない人にはかなり厳しいけど、エンジニアという職はこれからますます減り、豊富な経験を必要とするエリート職になっていくと思う。
