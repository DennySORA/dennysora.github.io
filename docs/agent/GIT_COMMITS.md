# Git Commit Policy

Load this playbook only when the user explicitly asks to create, amend, or rewrite a commit. An implementation request alone does not authorize a commit, push, tag, release, rebase, or history rewrite.

## 1. Scope and preflight

- Inspect `git status --short`, the complete working-tree diff, and the staged diff before committing.
- Preserve unrelated and pre-existing work. Stage only files or hunks owned by the requested change; never use broad staging when ownership is mixed.
- Run the relevant quality gates and `git diff --check`. The commit message must describe actual staged changes and executed validation, not intent or assumptions.
- Do not bypass hooks, signatures, branch protection, or repository policy unless the user explicitly requests it and the consequences are understood.
- A request to commit does not authorize a push. Push, force-push, tag, publish, release, amend, rebase, and history rewrite each require explicit matching scope.

## 2. Author and committer identity

The required name is `DennySORA`, using the contributor's already configured real email address.

- Verify author and committer identity before committing without printing the email into prose or logs.
- Do not guess an email, substitute a placeholder, use a shared/bot identity, or silently change local/global Git configuration.
- If the name is not `DennySORA`, the email is absent, or author and committer metadata would be noncompliant, stop before the commit and report the required correction. Changing identity requires separate user authorization.
- After committing, verify the resulting author, committer, message, and trailers before reporting success.

## 3. Conventional Commit header

Use:

```text
<type>(<scope>): <imperative summary>
```

When the change is genuinely repository-wide and no meaningful scope exists, this form is also valid:

```text
<type>: <imperative summary>
```

Allowed types are:

- `feat` — user-facing capability;
- `fix` — defect correction;
- `docs` — documentation only;
- `refactor` — behavior-preserving source restructuring;
- `perf` — performance improvement;
- `test` — test additions or corrections;
- `build` — build system or dependency changes;
- `ci` — continuous-integration changes;
- `chore` — maintenance outside source and tests;
- `style` — formatting or style-only changes;
- `revert` — a deliberate revert.

Use the smallest meaningful subsystem or top-level owner as the scope; omit it only when the change is genuinely repository-wide. Write the summary in English, imperative mood, without a final period. Prefer at most 50 characters and never exceed 72 characters. Describe the outcome, not the tool or work session.

## 4. Body and trailers

A body is mandatory for every non-trivial commit. Use concise bullets grounded in the staged diff:

```text
- What: <specific behavior, source, configuration, or contract changed>
- Why: <reason or problem addressed, when evidenced>

Tests: <exact checks run and their result>
```

- Add more `What:` bullets when needed; do not invent a `Why:` that cannot be inferred.
- If dependencies changed, name each package and say whether it was added, bumped, pinned, or removed. Mention the lockfile impact. The zero-tolerance metadata rule below is the sole exception: when a package's literal name contains a forbidden identifier, describe its ecosystem role and action without reproducing that identifier, and rely on the staged manifest and lockfile diff for the exact package name.
- `Tests:` must distinguish passed, failed, blocked, and not run. Never say tests passed when the stated command did not execute successfully.
- Use trailers intentionally and sparingly. `Co-Authored-By:` is permitted only for a real human collaborator whose attribution the user intends.

## 5. Breaking changes

For an incompatible public API, schema, persisted-state, CLI, configuration, or behavior contract:

- add `!` after the type or scope in the header; and
- add a `BREAKING CHANGE:` footer that explains the incompatibility and a concrete migration path.

Do not label an internal refactor as breaking, and do not hide a real breaking change in an ordinary body bullet.

## 6. Zero-tolerance attribution rule

Commit messages, author/committer names and emails, trailers, signatures injected into message text, and squash-derived text must contain none of the following:

- `Claude` or any case variation;
- `Anthropic` or any case variation;
- `anthropic.com` or an address at that domain;
- automated authorship or assistance attribution, generation signatures, or AI/tool/service/bot co-author entries.

Do not add wording such as “generated by” or “assisted by” for any automated tool. Remove automatically injected attribution before committing. Human co-authors are the only permitted co-authors.

The literal generic product terms `AI`, `assistant`, `tool`, `service`, and `bot` are allowed when they factually describe product behavior, architecture, dependencies, or scope. Only statements that attribute authorship, generation, or assistance to an automated system are prohibited by this clause; the separately forbidden vendor identifiers above remain prohibited wherever this metadata rule applies.

Perform a case-insensitive pre-commit scan of the complete proposed message and resolved identity fields. If any forbidden identifier or attribution is present, do not commit until it is removed.

This rule governs commit metadata, not repository content. Do not rename, remove, or misrepresent an evidenced dependency merely to make its source or manifest avoid a forbidden identifier. When a legitimate dependency name would violate the metadata scan, use a neutral but accurate phrase such as `the configured language-model SDK dependency` in the commit body; the staged manifest and lockfile remain the factual record. The zero-tolerance metadata rule takes precedence over the ordinary requirement to spell out package names.

## 7. Final verification

Immediately after the commit:

- inspect the committed file set and patch;
- inspect the full author, committer, subject, body, and trailers;
- confirm no unrelated path was included and the zero-tolerance rule passed;
- report the commit ID, subject, validation results, and whether the working tree still contains unrelated or uncommitted changes.

Never claim that a commit or push exists until Git verifies it.
