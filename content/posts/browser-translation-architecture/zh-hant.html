這套翻譯的工程核心，是把持續變動的網頁，整理成可排程、可重用、能核對身分後回寫的工作。翻譯服務負責產生文字；擴充套件負責讓結果在正確的時間、正確的位置出現。

01

沿著一段原文，看資料如何流過整個系統

Browser Script Manager 將翻譯與其他功能組裝成同一個 Manifest V3 擴充套件。下面追蹤預設網頁段落的翻譯流程：每條箭頭都標示傳遞內容；方塊所在泳道表示執行邊界。選取文字與翻譯中心的入口差異接在下一節。

兩個關鍵出口：07 發出帶版本的狀態與結果通知；片段完成後，仍要經過整段組裝與 DOM 提交。10 處理本機保存，失敗重試只回保存佇列。11 的同步回程寫入本機翻譯記憶，後續再由正常查詢使用。

為什麼要考慮 service worker 重新啟動？

Chrome 的 extension service worker 是事件驅動的，可能在閒置時結束；一般 JavaScript 全域變數不會自動保存。本專案因此把翻譯記憶與配額寫進 IndexedDB，並讓頁面在重連後重新宣告活躍需求。這是生命週期設計，不能解讀成 worker 永遠不會中斷。

03

先分清楚：位置、工作、請求

頁面綁定記錄畫面上的需求；共享工作代表一份可重用的翻譯任務；請求嘗試則是向特定翻譯資源執行的一次操作。

同時到達的兩個相同需求，如何避免重複送出？

背景排程器在第一次非同步記憶查詢之前，就把「正在查詢」的工作放進索引。後到的頁面需求訂閱同一份工作；即使前一個查詢尚未返回，也不另外建立相同任務。這讓非同步查詢期間的重複需求仍能合併。

04

擷取的是可辨識的原文，不是一整包 HTML

先辨識段落

依 DOM、顯示類型與排除規則走訪，跳過自己的輸出、隱藏內容與發音標記。

再拆成句子

使用瀏覽器文字分段能力；超過 2000 UTF-16 單位時，先找子句標點，再找字素邊界。

最後保留身分

每個片段保留原始範圍、分段順序與原文版本；原文變更後重新建立文字單位。

UTF-16、字形與 token 為什麼不能混在一起？

UTF-16 編碼單位是 JavaScript 字串長度使用的單位；emoji 可能占多個單位，多個 Unicode 碼點也可能組成一個使用者看到的字形。字素（grapheme）描述這類可視文字單位的分群；token 則由模型的分詞器決定。

預設 2000 是每個文字單位的字串長度限制。若單一字素已超過上限，就回報輸入過大；瀏覽器不支援文字分段時，備援只逐碼點處理，不能保證完整複合字形分群。

短片段另有本機啟發式：移除 URL 等雜訊後，單一拉丁字母詞可能被略過；含中日韓文字的短片段可保留。這降低零碎請求，也可能漏掉有意義的單字。選取翻譯不套用同一個頁面短文門檻。

延伸閱讀：瀏覽器的文字分段能力。

05

先服務正在讀的地方，再預載前方

頁面知道「原文在哪裡」；背景決定「現在值得翻哪一段」。預載區隨閱讀方向與速度改變，排程優先級則跨頁面統一比較。

展開預載公式與捲動演算法
前方範圍 = min(10000, max(設定邊距, round((倍數 + 提前量) × H))) 後方範圍 = min(設定邊距, round(0.5 × H)) 倍數：尚未捲動 1.5／閱讀中 3／快速掃讀 5 提前量：翻譯區 0／段落註冊區 0.5

當設定邊距≤0，兩邊都回 0。向上閱讀時交換上下方範圍。捲動速度用 EMA 平滑：α=1−exp(−dt/200)，新速度＝舊速度＋（瞬時速度−舊速度）×α。dt 的單位為 ms，瞬時速度的單位為 px/s；間隔達 400ms 時直接採新樣本。

轉向要累積 max(120px, 0.35H) 的反向移動；前向速度達 2.5 viewport/s 可進入快速掃讀狀態，維持 2 秒。這些門檻減少少量回拉造成的 觀察範圍重建；它們是工程啟發式，不是閱讀意圖辨識模型。

先讀位置，再更新畫面：頁面端先批次讀取段落位置，再插入佔位元素；後續翻譯流程重用可見性觀察器提供的位置資料，減少排版讀取與 DOM 寫入交錯。
06

規則先決定什麼能翻，再保護關鍵詞

規則優先順序與 Aho–Corasick 的精確分工

先處理整頁停用，再看整句保留原文／固定譯文、使用者釘選譯文、禁止外送，最後才做詞組佔位符替換。禁止外送仍允許顯示本機已保存的譯文。

Aho–Corasick 負責找到多個詞組；「最左、最長」是後續排序與游標選取共同決定的結果。掃描以 UTF-16 編碼單位進行，並不理解自然語言詞界。完整流程還包含命中展開與排序，不能直接把全部成本寫成 O(n)。

匹配範圍包含任意文字、整句精確比對與字面詞組，不提供任意正規表示式。編譯或比對失敗時，可退回較直接的參考掃描方式。

07

上下文要穩定，也要遵守同一套外送規則

啟用文件背景的翻譯設定，會在第一批送出前凍結候選文字。背景端再依目前政策挑出合格內容，避免「禁止翻的段落」透過其他句子的上下文被間接送出。

08

先問本機：這個語意契約，是否已經翻過？

資料層 保存策略 設計取捨
翻譯記憶 不設有效期限、不自動驅逐；預設 512 MiB 內容計數／20 萬筆／單筆 1 MiB 滿了拒絕新寫入，保住已有紀錄。數值不含整個 IndexedDB 索引與額外儲存成本。
舊版快取 預設 30 天／128 MiB；LRU 驅逐 可重建的快取，採用不同於已保存譯文的保留策略。
規則／釘選譯文 持久政策資料 使用者指定的行為，不是一般 LRU 快取。
換模型、換頁面，哪些結果可以重用？

頁面翻譯的語意身分不直接包含供應商或模型。其他語意條件相同時，換模型仍可能命中舊結果；「強制重新翻譯」才跳過翻譯記憶與舊版快取，結果驗證成功後替換同一語意鍵的記憶。

選取翻譯與翻譯中心使用各自的入口約定，翻譯設定中也包含供應商識別。因此翻譯中心的 A 供應商卡片不會使用 B 供應商卡片的結果；同一供應商設定更換模型，則保留原有身分。

上下文、規則與版本也納入語意契約，透過精確雜湊比對尋找譯文。不同頁面的相同句子，只有其他語意條件也相同才可共用；相似的文字不會自動命中。

09

合批節省請求，派送核准守住資源與配額

候選工作先依閱讀需求排序，再選擇可用的翻譯資源，最後嘗試合併成一批。批次大一點能合併工作；可見內容則採較小門檻，讓第一批結果不用等太多句。

900 不是每次請求的絕對字數上限：第一個項目先加入批次，追加其他項目時才檢查總長。單一已分句的翻譯單位可能超過 900；提示詞與上下文也不算在這個原文長度裡。UTF-16 編碼單位、模型 token 與網路位元組是三套不同的計量。

並行量

同時檢查全系統、單一翻譯資源與所有相關配額群組。初始預設上限分別是 16、12、16 個並行名額。

送出速率

每個翻譯資源的令牌桶預設每秒補充 8 次請求的容量，最多累積 16 次。它管理啟動節奏，不保證每秒完成 8 次。

時間窗配額

依設定檢查每分鐘請求數、每分鐘 token 數與每日請求數。實際用量較高時向上補記；較低或未回報時，不自動退還預扣量。

演算法：何時等待時間，何時等待事件？
D = S + P + a − L S = 已提交至時間窗帳本、尚未到期的保守扣帳 P = 尚未完成送出提交的預留量 a = 新需求　　L = 設定上限
條件 派送判斷 含義
a > L 阻擋需求 這筆需求本身超限，設定不變時，等待也無法容納。
D ≤ 0 通過這項配額檢查 還要繼續通過並行名額、送出速率與其他配額檢查。
0 < D ≤ S 等待指定時間 掃描時間格，找出足夠扣帳到期的時刻。
D > S 等待狀態變更 即使已提交扣帳全到期，待提交預留加上新需求仍超限。

同一翻譯資源的時間條件取最晚門檻；若還需要釋放名額或完成寫入，就等待相應事件。不同候選工作之間則找最早可能喚醒的時刻。固定容量的環狀時間格，避免記憶體隨歷史請求數無限增加：分鐘窗 62 格、每格 1 秒；日窗 1442 格、每格 60 秒。

扣帳所屬的時間格編號為 ceil（歸屬時間 ÷ 每格長度），也就是向上取整。建立持久化快照時，待提交扣帳的歸屬時間至少設到當下加 1000ms；交易完成後，再確保它不早於當下，採保守到期。請求令牌桶使用整數計數，一次請求等於 1,000,000 個微量單位；這與模型切分文字的 token 無關。

演算法：資源選擇、token 估算與可選的自適應

多個翻譯資源可用時，先比較「候選視窗內的相容需求量 ÷ 可用並行數」，分母至少取 1；再比較負載、路由優先度與穩定的資源識別順序。這是從眼前候選中挑選資源的啟發式，沒有求解全域最佳配置。

估算基底 = ceil（所有字元權重之和）+ 4 字元權重：Unicode 碼位大於 0x2E80 時取 1，否則取 0.34 互動式完整提示詞：ceil（各非空片段基底之和 × 1.2）+ 256 互動式輸出預留：請求指定的上限，未指定則為 4096

這是本機決定能否派送時的估算，與供應商實際切分 token 的方式可能不同，也無法代替帳戶的剩餘額度。頁面批次還會把翻譯指令與上下文加入估算，不能只拿原文字數當每分鐘 token 用量。

自適應並行量預設關閉。啟用後，並行上限從硬上限的一半向上取整開始。成功回應到達時，若統計窗已滿 20 秒，就檢查前一窗是否至少成功 10 次、仍有待辦工作且沒有壅塞；符合才增加 1 個名額。容量壅塞時減半，同一調整週期最多下降一次。自動備援切換也預設關閉，需要明確啟用才會在符合條件時改用其他資源。

10

模型回傳的是資料協定，通過驗證才成為譯文

預設的頁面批次翻譯，使用簡短編號對應每一項結果。輸出順序可以不同；編號、譯文與佔位符都必須通過驗證。這讓「整包壞掉」與「只有幾個項目需要修復」可以分開處理。

翻譯服務 實際網路行為 回覆要求
DeepSeek／OpenAI／Google 底層關閉自動重送，每次操作最多發出 1 次網路請求；重試交由上層排程管理。自訂服務網址仍須符合對應服務的連線規則。 串流文字交給回覆解析器，必須符合結構化資料格式。
Microsoft 一次操作內，先取得 Edge 認證，再送出翻譯；兩個階段各限 1 次網路請求，合計最多 2 次。 檢查回傳筆數，按原位置補上相同項目編號，轉成統一格式。
哪些容錯被允許？哪些數字不是 token 上限？

解析器容許以指定標記包住的前置思考段落，以及完整包住回覆、未標語言或標成 JSON 的Markdown 圍欄；合法空白與資料欄位換序也可接受。任意散文中的 JSON 不會被猜測擷取。大量串流增量會切成 32,768 個 UTF-16 單位的片段處理，跨片段保留文字、跳脫符號與 Unicode 的解析狀態。

界線 預設值 計量方式
整份文字回覆 262,144 2 × UTF-16 長度，含外框文字
模型回覆的網路資料量 16 MiB 文字回覆預算 × 64，包含 SSE 與 JSON 外框
單項譯文 24,000 UTF-16 編碼單位

產品方向是「來源自動辨識 → 臺灣繁體中文」。頁面翻譯與共用設定採用不同的繁體中文語言標記；Microsoft 另外透過 ISO 語言對照表轉換，找不到對應時使用繁體中文標記。跨服務連接時，需要處理這層語言表示的差異。

系統提示詞要求忽略原文與上下文中的指令，譯文內容使用純文字。這能表達預期行為，仍無法保證完全消除提示詞注入或翻譯錯誤。DeepSeek 預設關閉思考模式，使用者也可自行調整。

11

回來得再快，也要先確認頁面還是那一份

動態網頁可能在翻譯途中改字、換段落、離開頁面，使用者也可能正在反白。背景完成只代表取得候選結果；真正更新網頁節點前，還要核對當下的原文與操作狀態。

顯示模式 原文怎麼處理 譯文怎麼寫入
雙語 原文留在原位；已有舊譯文時，等新的更新方案提交才替換。 建立容納譯文的節點，再交由呈現佇列更新。
純譯文 暫存原來的節點物件，再移出頁面；還原時插回同一批節點。 主要路徑使用文字與換行節點組合譯文；模型文字不當作 HTML 執行。
更細的呈現策略：合併、延後與避免不必要的重寫

呈現節奏控制器合併陸續抵達的結果，依最近一次工作的耗時調整節奏：新成本估值 = 0.6 × 舊成本估值 + 0.4 × 本次耗時；下一輪間隔為 min（1000ms，2 × 新成本估值）。瀏覽器的動畫影格通知尚未到達時，另有 250ms 的計時器補位。這裡追蹤的是工作耗時，無法完整代表瀏覽器排版與繪製的成本。

同一區塊只保留最新的等待更新方案；最多保留 128 份延後方案，超過後可改記「需要重新整理」，這類記號上限為 4096。頁面變動的重新比對則合併成每段一個進行中的工作，再加一個待重跑記號。

呈現摘要使用「文字長度＋32 位元 FNV-1a 雜湊」判斷能否略過重寫，與背景使用 SHA-256 的語意識別不同；不同內容仍可能得到相同摘要。多句譯文依原翻譯單位的順序組合，接縫以中、日、韓文字的空白規則推估，並不逐字還原原始空白。

保留同一批原始節點，有利於延續原有物件關係；事件綁定、排版與互動效果，仍受到網站本身的結構與更新方式影響。

12

讀得到譯文，不等於已經存好

保存佇列如何限制記憶體？
區域 筆數上限 估計位元組上限
主要保存佇列 32 16 MiB
額外等候區 64 8 MiB
保存失敗後保留的內容 64 8 MiB

等候或保存失敗的內容，有效保留期為 10 分鐘，於後續佇列操作或重試時檢查清理。容量估計為「原文 UTF-8 位元組＋譯文 UTF-8 位元組 × 2＋1024」，與實際記憶體占用可能不同。佇列滿時，會暫停新的頁面翻譯派送；已發出的請求可完成。

這個佇列只保存在執行中的記憶體。背景服務結束時，尚未完成寫入的內容，不會因重啟自動恢復。圖中呈現的是頁面翻譯的保存狀態；互動式入口只將內容排入保存工作，不等待同一套完整的畫面狀態流程。

20 s串流無新內容的期限
90 s單次嘗試的逾時門檻
5 s取消後等待終止的寬限期

以上為可調整的預設值。一般頁面重試策略以 4 次實際送出為預設門檻，包含首次；累計執行時間預算為 180 秒。過大的多項目批次另有拆成單筆重新排隊的修復路徑。從未嘗試、只在畫面外等待的需求，不套用一般 30 分鐘的需求到期限制。

失敗 處理方向 為什麼分開
HTTP 401／一般 403／404 視為認證、權限或模型設定問題，阻擋相關翻譯資源。 盲目重送不會修好設定。
HTTP 429 · 容量類 對受限的資源或配額範圍設定冷卻期；工作留在佇列，等待資源再次可用。 讓負載下降後才再試。
HTTP 402／429 · 付費或額度不足 預設不再重試；額度類 403 也屬此類。明確啟用備援切換，且有符合獨立備援條件的可用資源時，仍可轉送。 付費／帳戶額度問題不是瞬時壅塞。
HTTP 408／409／425／5xx 視為暫時性的伺服器失敗，可以重試。 有機會隨時間恢復，仍受次數與預算限制。
HTTP 413／過大輸入 多項目批次拆成單筆重試；單筆仍過大則阻擋該工作。 批次過大，不代表每個項目都無法單獨翻譯。
重試時間、喚醒與時鐘跳動

一般工作的延後重試，使用完整隨機抖動：每次從零到等待上界之間取一個隨機延遲。容量型 HTTP 429 則對受限的資源或配額範圍設定冷卻期，採用伺服器指定的等待時間；未提供時使用基礎延遲，不套用隨機抖動。

等待上界 = min（延遲上限，基礎延遲 × 2^(已嘗試次數−1)） 可重試時間 = max（伺服器指定時間， 現在 + floor（隨機值 × 等待上界）） 隨機值介於 0（含）與 1（不含）；floor 表示向下取整

隨機抖動讓重試時間分散；回應標頭 Retry-After 指定的時間是額外下限，可接受秒數或 HTTP 日期，並考慮伺服器時間差。伺服器要求的等待時間最多保留 7 天。

喚醒排程合併成一個最早到期的計時器；預期等待至少 30 秒時，再以瀏覽器的背景鬧鐘補充喚醒。時鐘檢查會比較系統時間與單調時鐘各自經過了多久：偏移超過 5 秒，或系統時間倒退超過 5 秒，就暫停新的派送。沒有新異常且穩定期達 2 秒後，才依保守策略恢復。

取消圖描述已送出的網路嘗試。已保留名額但尚未送出的嘗試，可先結束並釋放名額；若進行中的扣帳交易隨後成功提交，即使沒有真的呼叫服務，也會保留該筆保守扣帳。無法確認是否終止的網路操作，會隔離相關資源並保留名額；收到遲來的終止通知後才釋放。背景服務重啟後建立新的執行代次，舊請求不再占用並行名額，已知的配額帳本則繼續保留。
